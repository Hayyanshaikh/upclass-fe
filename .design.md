# Frontend design rules

Read this file before creating or changing any screen or UI component. Follow the existing system theme and reuse existing components. Keep the implementation simple and consistent.

## Theme is the source of truth

- Read `app/globals.css` for the current Tailwind `@theme` tokens.
- Read `components/layout/AntdProvider.tsx` for shared Ant Design defaults.
- Use semantic theme classes for text, backgrounds, borders and radii. Do not hardcode hex, RGB, HSL, pixel radii or font sizes in screens.
- Do not copy existing hardcoded values into new code. Older overrides are not design rules.
- If a genuinely new shared token is needed, define it centrally in `@theme` and then use its named utility. Avoid one-off arbitrary values and inline `style` props.
- Keep AntD component defaults in `AntdProvider`. Prefer supported theme tokens over deep CSS selectors and `!important` overrides in screens.
- Match AntD defaults to the global theme. Do not introduce a different palette in the provider.

| Purpose | Classes |
| --- | --- |
| Brand and primary actions | `text-primary`, `bg-primary` |
| Accent | `text-secondary`, `bg-secondary` |
| Success | `text-success`, `bg-success/10` |
| Warning | `text-warning`, `bg-warning/10` |
| Error or overdue | `text-danger`, `bg-danger/10` |
| Main text | `text-dark` |
| Secondary text | `text-gray` |
| Text on dark surfaces | `text-light` or `text-background` |
| Cards and dialog surfaces | `bg-background` |
| Page background | `bg-foreground` |
| Standard border | `border border-border` |
| Border on sidebar | `border-border-light` |

Use named opacity utilities such as `bg-success/10` for soft status backgrounds. Never use classes such as `bg-[#dceee8]`, `text-[#805100]` or `rounded-[14px]` in new screens.

## Spacing, sizing and typography

- Use Tailwind's spacing scale: `gap-2`, `gap-3`, `gap-4`, `gap-6`, `p-4`, `p-6`, `px-5`, `mt-4`, etc.
- Match surrounding screens instead of inventing new spacing for each page.
- Typical defaults: `gap-3` for actions, `gap-4` for form fields, `gap-4` or `gap-6` for grids, and `p-6` for card/dialog content.
- Use `rounded-xs`, `rounded-sm`, `rounded-md`, `rounded-lg`, `rounded-xl` or `rounded-2xl` from the theme. `rounded-full` is appropriate for avatars and pills.
- Use standard text classes such as `text-xs`, `text-sm`, `text-base`, `text-lg`, `text-xl` and `text-2xl`. Keep normal form/dialog text compact.
- Use the globally configured Manrope font. Do not set a separate font per screen.
- Preserve shared component sizes. Buttons and form controls use the provider's default height; do not enlarge them independently for a screen.
- Nav items use `min-h-11`, `gap-3`, `px-3.5`, `py-0`, `rounded-sm`, `text-sm` and `font-semibold`.
- Prefer responsive layout utilities, flex and grid to fixed dimensions. Existing shared defaults such as dialog width belong in the shared component, not repeated throughout pages.

## Reuse the existing components

Inspect component code and its props before using it. Extend an existing component when appropriate rather than duplicating it.

| Component | Use |
| --- | --- |
| `components/ui/Input.tsx` | Text and password fields; owns its AntD `Form.Item`, label and validation |
| `components/ui/Select.tsx` | Dropdown fields; owns its AntD `Form.Item`, label and validation |
| `components/ui/Checkbox.tsx` | Checkbox fields with form binding |
| `components/ui/Button.tsx` | Primary, secondary and link actions, including loading and disabled states |
| `components/ui/Dialog.tsx` | Shared dialog header, body and footer |
| `components/ui/Table.tsx` | Generic table, scrolling and pagination for any record type |
| `components/ui/StatCard.tsx` | Dashboard metrics |
| `components/shared/PageHeader.tsx` | Screen title and subtitle |
| `components/shared/Logo.tsx` | Branding with `sm`, `md` or `lg` size |
| `components/layout/Sidebar.tsx` | Dashboard navigation |

- Use Ant Design inside reusable UI components. Screens should consume these wrappers rather than recreating Input, Select, Button, Table or Modal directly.
- Keep feature-specific forms in `components/forms` and feature dialogs in `components/dialogs`.
- `Input` and `Select` accept `name`, `label`, `rules` and `isRequird`. Preserve the existing prop spelling. Do not wrap them in another named `Form.Item`.
- Use `Button variant="link"` for text button actions. Use Next.js `Link` for actual navigation where appropriate.
- `Dialog` accepts a string or React node through `title`, body through `children`, and defaults to Ok/Cancel footer buttons. Customize text using `okText`/`cancelText`; use `onConfirm` and `onClose` for actions.
- Feature dialogs should compose `Dialog`, not recreate modal structure and footer buttons.
- Keep `Table` generic. Define page-specific columns and renderers at the feature/page level; pass `columns` and `data` to it.
- Use `react-icons/lu` for icons. Avoid handwritten SVG markup when a matching icon exists.

## Code organization

- Put custom type declarations in `types/`, grouped by their purpose. Import with `import type`.
- Keep prop types explicit and easy to read. Avoid unnecessary `Omit`, `Pick`, intersections and inherited prop trees.
- Put menu definitions, mock records and other shared static data in `constants/`.
- Use short, clear component names. Break larger components into small functions in the same file when that makes them easier to read.
- Keep pages focused on composing components and handling feature behavior.

## API integration flow

Use the same data flow across screens when replacing preview data with backend data. Follow the existing Users listing and User form patterns where they apply.

- Use the Orval-generated hooks, DTOs and query keys from `app/api/endpoints` and `app/api/schemas`. Run `npm run api:generate` when the backend contract changes. Do not edit generated files or create another request hook for an endpoint already generated by Orval.
- Keep shared HTTP configuration and auth headers in `app/api/axios-instance.ts`. Map API responses to UI models in `lib/api/` when the screen needs a different shape; keep the generated DTOs as the source of truth for request and response types.
- For server-backed listings, use `useTable` as the single source of page, page size, offset, search and filter values. Pass those values to the generated list hook using the endpoint's actual query parameter names. Avoid separate state for each filter or local filtering/pagination of server results.
- Pass the API records, total count and fetching state to the shared `Table`. Connect `current`/`onPageChange`, `search`/`setSearch`, and `filterValues`/`onFilterValuesChange` to `useTable`. Define columns, filter fields, search configuration and actions before the JSX return. The toolbar form sends filter changes through `onFilterValuesChange`; individual filters do not need their own state.
- Use generated mutation hooks for create, update and delete. Show pending and error states. After a mutation on a listing screen, call that listing hook's `refetch()`; when a form navigates back to its listing, the listing hook refetches on mount. Do not use `useQueryClient` or manual query-key invalidation inside screens and forms. Keep navigation and permission checks in the feature screen or form.
- Handle loading, empty and error states from the real API. Do not leave preview store data or mock records driving an integrated screen, and do not show success when a request fails.
- Apply this flow to each screen as its API becomes available. Extract shared logic only when multiple screens need it; keep endpoint-specific mapping and behavior close to the feature.

## Layout and scrolling

- Reuse the auth and dashboard route layouts. Do not repeat their branding/sidebar in pages.
- Dashboard sidebar stays stationary; its menu scrolls independently.
- Normal dashboard content scrolls in the right panel, not the document body.
- Table screens use a height-constrained flex column with `h-full`, `min-h-0` and `overflow-hidden`. Keep the page header outside the table scroll area.
- Let the reusable Table manage available row height and keep pagination visible. Do not add a second competing page scrollbar.
- Use the global scrollbar styling. Do not add browser-default bulky scrollbars or a separate scrollbar design per screen.
- Support small screens with responsive grids and horizontal table scrolling.

## Desktop and mobile are separate surfaces

- The theme, tokens, typography, component reuse and API flow rules above are shared by both platforms. The mobile section below extends them.
- Both platforms use the SAME routes under `app/(dashboard)`. There is no `/m` prefix and no separate mobile route group.
- `app/(dashboard)/layout.tsx` picks the shell with `useIsMobile` (matches `max-width: 767px`): mobile gets the app bar, scrollable `main` and bottom navigation; desktop keeps the sidebar.
- A page renders both presentations through `components/shared/PlatformSwitch`, e.g. `desktop={<Subjects />}` and `mobile={<MobileSubjects />}`. PlatformSwitch hides the desktop wrapper below `md` and the mobile wrapper at `md` and up.
- The desktop wrapper in `PlatformSwitch` must keep `h-full` (`hidden h-full md:block`). Desktop table screens depend on that height chain; removing it collapses the shared Table body.
- Mobile presentation is a separate component tree under `components/mobile/`. Never reuse desktop page layouts, tables, sidebars, page headers or dialogs in mobile UI, and never import desktop feature components into mobile components or vice versa.
- APIs, auth, permissions, hooks, DTOs and business logic stay shared. Do not duplicate requests or mapping; both surfaces call the same generated hooks.
- Do not shrink, restack or hide parts of a desktop page to create a mobile screen. Responsive behavior that keeps a desktop screen usable in a narrow browser is not a mobile design.

## Mobile design system

Applies to every mobile presentation rendered through `PlatformSwitch`. It uses the same global theme and is a separate component system, not a resized desktop.

### Foundation

- Use the existing `@theme` tokens in `app/globals.css`: colors, `rounded-*`, spacing scale and the Manrope font. Do not introduce a mobile-only palette, font or brand color.
- Use the same semantic classes as desktop: `bg-background`, `bg-foreground`, `text-dark`, `text-gray`, `text-primary`, `text-danger`, `border-border`, `bg-success/10`. Do not hardcode colors, radii, font sizes or shadows.
- Keep the global `AntdProvider` defaults. Mobile-specific Modal, Drawer and sheet behavior belongs to mobile wrappers, not to new global overrides.
- Reuse the generic wrappers in `components/ui` (`Button`, `Input`, `Select`, `Checkbox`, `DatePicker`, `TimePicker`, `TextArea`, `MultiSelect`, `StatusBadge`, `TagList`) for fields and text actions. Mobile-only primitives live in `components/mobile/ui`; do not fork a shared control.
- Mobile primitives: `MobileList` + `MobileListFilters` (search, filter sheet, skeleton/empty/error, Load more), `MobileIconButton` (variants `appBar` default, `secondary`, `ghost`, `danger`, `fab`), `MobileSection`, `MetricTile`.
- Mobile dialogs live in `components/mobile/dialogs` (`MobileConfirmDialog`, `MobileFeedbackDialog`); never render a desktop dialog on mobile.
- Every button comes from a component: icon-only actions use `MobileIconButton` with a variant, text actions use the shared `Button`. Do not hand-roll styled `<button>`s. The only accepted raw `<button>` is a full card/row tap target.
- Mobile shell parts live in `components/mobile/layout/` (`MobileAppBar`, `MobileBottomNav`). Do not build per-screen headers or navigation.
- Use `react-icons/lu`. Do not add a mobile UI, gesture, carousel or animation dependency.

### Shell and layout

- `app/(dashboard)/layout.tsx` renders the mobile shell when `useIsMobile` is true: global green app bar (`MobileAppBar`), scrollable content and `MobileBottomNav`. Pages provide content only.
- Shell structure: `flex h-dvh flex-col overflow-hidden bg-foreground`; app bar `shrink-0`; `main` `min-h-0 flex-1 overflow-y-auto overscroll-contain px-4 py-4`; bottom navigation `shrink-0`. The document body must not scroll.
- Page spacing is `gap-4` between sections; card-list spacing is `gap-3`. When a floating action button is present the screen root adds `pb-20` so the last card clears the navigation.
- Single column by default. Use two columns only for compact metric pairs; never reproduce a desktop grid, sidebar or wide table.
- Respect `env(safe-area-inset-top)` in the app bar and `env(safe-area-inset-bottom)` in the bottom navigation and FAB offset only.
- No breadcrumbs, sidebar, drawer navigation or desktop page header inside mobile content. Shell variations use props, not copied shells.

### Header and page title

- `MobileAppBar` is global, not per screen: green surface (`bg-primary`, `text-background`, `rounded-b-2xl`), boxed greeting with the user's name and school pill, plus profile/settings, notices and logout icon actions.
- App bar icon actions use `MobileIconButton` (`appBar` variant): `min-h-11 min-w-11` with an accessible label and `react-icons/lu` at 18-20px.
- Screens do not add a second app bar. Content starts with the screen title as `text-lg font-bold text-dark` (e.g. `<h1>Subjects</h1>`), followed by the list toolbar.
- Keep the app bar visible while content scrolls; do not use overlapping absolute or fixed headers.

### Bottom navigation

- One bottom navigation per shell with 4-5 permission-filtered primary destinations; every item has an `Lu*` icon and a `text-xs` label (`min-h-16` row plus `pb-2`, active icon inside a primary pill).
- Use `bg-background`, `border-t border-border`, active item `text-primary`, inactive item `text-gray`.
- Filter navigation with the same permission keys as desktop; never show unauthorized destinations.
- Each tab points to a root route. Nested screens keep the navigation and mark the owning tab active.
- Do not use a hamburger menu, desktop sidebar or Drawer as primary mobile navigation.

### Cards and list items

- Mobile listings are card lists, never tables. Card: `rounded-lg border border-border bg-background p-4`; separate cards with `gap-3`; 4-5 cards should fit on a phone screen.
- Hierarchy: title `text-sm font-semibold text-dark`, supporting meta `text-xs text-gray`, optional `StatusBadge`/`TagList`, and a muted trailing chevron for navigation. Do not add per-card action rows; compact cards win over large buttons.
- The card itself is the tap target and opens the record (edit sheet). Use a trailing chevron (`LuChevronRight`, `text-gray`) as the affordance.
- Create is a fixed circular FAB at the bottom-right, above the bottom navigation: `MobileIconButton variant="fab"` (~56px, `bg-primary`, shadow, `bottom-[calc(5rem+env(safe-area-inset-bottom))]`). Do not put Add in the screen heading.
- Destructive actions live inside the opened record (see sheets), not on every card. If the role can delete but not edit, a `MobileIconButton variant="danger"` may sit at the card trailing edge.
- Use `StatCard` only when its density fits mobile; otherwise use compact metric tiles from `components/mobile/ui`. Do not place a desktop table inside a horizontal scroller on a dedicated mobile screen.

### Forms

- Single column with labels above fields, full-width controls and `gap-4` between fields. One field per row.
- Compose the existing `Input`, `Select`, `Checkbox`, `DatePicker`, `TimePicker`, `TextArea`, `MultiSelect` wrappers; mobile form composition lives in `components/mobile/forms`.
- Keep the existing `name`, `label`, `rules` and `isRequird` contract. Do not create parallel mobile input components or duplicate validation.
- Forms open as bottom sheets (`MobileSubjectForm` is the reference): swipe handle, title with a ghost close `MobileIconButton`, a scrollable field area (`min-h-0 flex-1 overflow-y-auto pb-1`), and a sticky footer (`border-t border-border`) with Cancel (`Button variant="secondary"`) and the primary Save (`Button type="submit"`).
- Delete is a `MobileIconButton variant="danger"` in that sticky footer beside Cancel/Save, so it is always visible and never requires scrolling.
- Show validation inline under the field, keep the active field visible above the keyboard, and set appropriate input types and autocomplete where the shared control supports them.
- Shared control heights do not change. Reach 44px (`min-h-11`) touch targets by enlarging the tappable row or card, not the shared control default.

### Dialogs and sheets

- Mobile dialogs and sheets come from `components/mobile/dialogs` and `components/mobile/ui`; do not render desktop `Dialog`, `DeleteDialog`, `SuccessDialog` or `ErrorDialog` on mobile.
- `MobileConfirmDialog` confirms deletes and other destructive actions before the API call.
- `MobileFeedbackDialog` reports success and error outcomes after mutations. Mobile feedback uses these sheets, not toasts.
- Filter sheets use the generic `MobileListFilters`: swipe handle, title with a ghost close button, one field per row, then a full-width row with Reset (`secondary`) and Apply (`primary`).
- Sheets are bottom-anchored, full width, `rounded-t-2xl`, capped in height with a scrollable body and a sticky action footer.
- Keep focus trapping, accessible titles, close labels and back/close behavior; the close control uses a `min-h-11` target.

### Lists, search and filters

- Reuse the generic `MobileList` (`components/mobile/ui/MobileList.tsx`, types in `types/mobile-list.ts`) instead of hand-rolling listing markup. It mirrors desktop `Table.tsx`: the screen owns data via `useTable` + generated hooks and passes `items`, `rowKey`, `renderItem`, `search`, `filters`, loading flags, `hasMore`/`onLoadMore`, `resetSignal` and `emptyText`.
- `MobileList` owns the search input and filter trigger in one row, the filter sheet (`MobileListFilters`), skeleton/empty/error states with retry, and the "Load more" button. `filters` takes `fields`, `values` (`useTable` filters) and `onApply` (`setFilters`); values are `Partial<TFilters>` exactly like desktop `Table`.
- Keep `useTable` as the source of page, page size, offset, search and filters, and pass the endpoint's real query parameters. Filter server-side, never client-side.
- Keep the active filter count visible as a badge on the filter trigger; applying the sheet resets to the first page.
- Use "Load more" (or infinite scrolling) with accumulated items instead of the desktop pagination footer. Keep page and page size in `useTable`.
- Show skeletons inside the list area while loading so the app bar, title, search and filters stay visible. Show inline empty and error states with a retry action that calls the listing hook's `refetch()`; reserve full-screen loaders for initial boot.
- After a successful delete, reset the whole listing: clear search, filters and page, remove the card from local state immediately, and increment `resetSignal` so `MobileList` clears the search field; call `refetch()` only when no query state actually changed.
- Gate create, edit and delete UI with `useRolePermission` for the module; a backend 403 alone is not enough.

### Interactions

- Minimum `min-h-11`/`min-w-11` tap targets (44px) and visible pressed states using `active:` classes. No hover-only affordances.
- Use `MobileIconButton` variants (`appBar`, `secondary`, `ghost`, `danger`, `fab`) or the shared `Button`; no ad-hoc styled buttons.
- Place primary actions within thumb reach at the bottom; separate destructive actions and confirm them first.
- Keep one primary action per screen; put overflow actions in a bottom action sheet.
- Use short transitions and respect reduced motion. Do not add animation or gesture libraries.
- Ensure correct keyboard behavior: input types, next/submit flow, and no content hidden behind the keyboard, sticky action footer or bottom navigation.
- Preserve accessible names for icon-only controls and visible focus styles for keyboard and assistive input.

### Consistency checklist

- Every mobile screen renders through `PlatformSwitch` on the same route, inside the same shell, app bar and bottom navigation.
- Every listing reuses `MobileList` with the same card, search, filter sheet, empty and loading patterns.
- Every action uses `MobileIconButton` (with a variant) or the shared `Button`; no raw styled `<button>` except full-card tap targets.
- Reuse existing mobile primitives before adding a new one. A new pattern is added to `components/mobile/ui` once and reused.
- No desktop page components, layouts, tables or dialogs on mobile; no mobile components on desktop.
- No hardcoded colors, radii, font sizes, shadows or spacing outside the shared tokens.

## Before finishing

- Confirm existing wrappers were reused and all new custom types/constants are in their folders.
- Check for hardcoded colors, radii, arbitrary spacing and inline styles; replace them with shared tokens/utilities.
- Preserve keyboard focus, accessible labels, validation, empty states and loading states.
- For desktop changes, verify the desktop route still renders; for mobile changes, verify the mobile shell, safe areas and bottom navigation.
- For shared component or hook changes, check one desktop screen and one mobile screen.
- On mobile, confirm the page renders through `PlatformSwitch`, reuses `MobileList`, uses component buttons (`MobileIconButton`/`Button`), keeps 44px (`min-h-11`) tap targets, places the FAB above the bottom navigation, and shows loading, empty and error states inside the content area. Confirm the desktop presentation still renders on the same route.
- For deletes on mobile, confirm `MobileConfirmDialog` runs before the API call, outcomes use `MobileFeedbackDialog`, and the listing resets (search, filters, page, `resetSignal`).
- Do not show fake successful backend actions. Clearly handle unavailable functionality.
- Run the appropriate checks for code changes, including TypeScript when types or component props change.
