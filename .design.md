# Frontend design rules

Read this file before creating or changing any screen or UI component. Follow the existing system theme and reuse existing components. Keep the implementation simple and consistent.

## Theme is the source of truth

- Read `app/globals.css` for the current Tailwind `@theme` tokens.
- Read `components/layout/AntdProvider.tsx` for shared Ant Design defaults.
- Use semantic theme classes for text, backgrounds, borders and radii. Do not hardcode hex, RGB, HSL, pixel radii or font sizes in screens.
- Do not copy existing hardcoded values into new code. Older overrides are not design rules.
- If a genuinely new shared token is needed, define it centrally in `@theme` and then use its named utility. Avoid one-off arbitrary values and inline `style` props.
- Keep AntD component defaults in `AntdProvider`. Prefer supported theme tokens over deep CSS selectors and `!important` overrides in screens.
- Match AntD defaults to the global theme. Do not introduce a different palette in the provider.

| Purpose | Classes |
| --- | --- |
| Brand and primary actions | `text-primary`, `bg-primary` |
| Accent | `text-secondary`, `bg-secondary` |
| Success | `text-success`, `bg-success/10` |
| Warning | `text-warning`, `bg-warning/10` |
| Error or overdue | `text-danger`, `bg-danger/10` |
| Main text | `text-dark` |
| Secondary text | `text-gray` |
| Text on dark surfaces | `text-light` or `text-background` |
| Cards and dialog surfaces | `bg-background` |
| Page background | `bg-foreground` |
| Standard border | `border border-border` |
| Border on sidebar | `border-border-light` |

Use named opacity utilities such as `bg-success/10` for soft status backgrounds. Never use classes such as `bg-[#dceee8]`, `text-[#805100]` or `rounded-[14px]` in new screens.

## Spacing, sizing and typography

- Use Tailwind's spacing scale: `gap-2`, `gap-3`, `gap-4`, `gap-6`, `p-4`, `p-6`, `px-5`, `mt-4`, etc.
- Match surrounding screens instead of inventing new spacing for each page.
- Typical defaults: `gap-3` for actions, `gap-4` for form fields, `gap-4` or `gap-6` for grids, and `p-6` for card/dialog content.
- Use `rounded-xs`, `rounded-sm`, `rounded-md`, `rounded-lg`, `rounded-xl` or `rounded-2xl` from the theme. `rounded-full` is appropriate for avatars and pills.
- Use standard text classes such as `text-xs`, `text-sm`, `text-base`, `text-lg`, `text-xl` and `text-2xl`. Keep normal form/dialog text compact.
- Use the globally configured Manrope font. Do not set a separate font per screen.
- Preserve shared component sizes. Buttons and form controls use the provider's default height; do not enlarge them independently for a screen.
- Nav items use `min-h-11`, `gap-3`, `px-3.5`, `py-0`, `rounded-sm`, `text-sm` and `font-semibold`.
- Prefer responsive layout utilities, flex and grid to fixed dimensions. Existing shared defaults such as dialog width belong in the shared component, not repeated throughout pages.

## Reuse the existing components

Inspect component code and its props before using it. Extend an existing component when appropriate rather than duplicating it.

| Component | Use |
| --- | --- |
| `components/ui/Input.tsx` | Text and password fields; owns its AntD `Form.Item`, label and validation |
| `components/ui/Select.tsx` | Dropdown fields; owns its AntD `Form.Item`, label and validation |
| `components/ui/Checkbox.tsx` | Checkbox fields with form binding |
| `components/ui/Button.tsx` | Primary, secondary and link actions, including loading and disabled states |
| `components/ui/Dialog.tsx` | Shared dialog header, body and footer |
| `components/ui/Table.tsx` | Generic table, scrolling and pagination for any record type |
| `components/ui/StatCard.tsx` | Dashboard metrics |
| `components/shared/PageHeader.tsx` | Screen title and subtitle |
| `components/shared/Logo.tsx` | Branding with `sm`, `md` or `lg` size |
| `components/layout/Sidebar.tsx` | Dashboard navigation |

- Use Ant Design inside reusable UI components. Screens should consume these wrappers rather than recreating Input, Select, Button, Table or Modal directly.
- Keep feature-specific forms in `components/forms` and feature dialogs in `components/dialogs`.
- `Input` and `Select` accept `name`, `label`, `rules` and `isRequird`. Preserve the existing prop spelling. Do not wrap them in another named `Form.Item`.
- Use `Button variant="link"` for text button actions. Use Next.js `Link` for actual navigation where appropriate.
- `Dialog` accepts a string or React node through `title`, body through `children`, and defaults to Ok/Cancel footer buttons. Customize text using `okText`/`cancelText`; use `onConfirm` and `onClose` for actions.
- Feature dialogs should compose `Dialog`, not recreate modal structure and footer buttons.
- Keep `Table` generic. Define page-specific columns and renderers at the feature/page level; pass `columns` and `data` to it.
- Use `react-icons/lu` for icons. Avoid handwritten SVG markup when a matching icon exists.

## Code organization

- Put custom type declarations in `types/`, grouped by their purpose. Import with `import type`.
- Keep prop types explicit and easy to read. Avoid unnecessary `Omit`, `Pick`, intersections and inherited prop trees.
- Put menu definitions, mock records and other shared static data in `constants/`.
- Use short, clear component names. Break larger components into small functions in the same file when that makes them easier to read.
- Keep pages focused on composing components and handling feature behavior.

## API integration flow

Use the same data flow across screens when replacing preview data with backend data. Follow the existing Users listing and User form patterns where they apply.

- Use the Orval-generated hooks, DTOs and query keys from `app/api/endpoints` and `app/api/schemas`. Run `npm run api:generate` when the backend contract changes. Do not edit generated files or create another request hook for an endpoint already generated by Orval.
- Keep shared HTTP configuration and auth headers in `app/api/axios-instance.ts`. Map API responses to UI models in `lib/api/` when the screen needs a different shape; keep the generated DTOs as the source of truth for request and response types.
- For server-backed listings, use `useTable` as the single source of page, page size, offset, search and filter values. Pass those values to the generated list hook using the endpoint's actual query parameter names. Avoid separate state for each filter or local filtering/pagination of server results.
- Pass the API records, total count and fetching state to the shared `Table`. Connect `current`/`onPageChange`, `search`/`setSearch`, and `filterValues`/`onFilterValuesChange` to `useTable`. Define columns, filter fields, search configuration and actions before the JSX return. The toolbar form sends filter changes through `onFilterValuesChange`; individual filters do not need their own state.
- Use generated mutation hooks for create, update and delete. Show pending and error states, then refresh affected queries with Orval-generated query keys after a successful mutation. Keep navigation and permission checks in the feature screen or form.
- Handle loading, empty and error states from the real API. Do not leave preview store data or mock records driving an integrated screen, and do not show success when a request fails.
- Apply this flow to each screen as its API becomes available. Extract shared logic only when multiple screens need it; keep endpoint-specific mapping and behavior close to the feature.

## Layout and scrolling

- Reuse the auth and dashboard route layouts. Do not repeat their branding/sidebar in pages.
- Dashboard sidebar stays stationary; its menu scrolls independently.
- Normal dashboard content scrolls in the right panel, not the document body.
- Table screens use a height-constrained flex column with `h-full`, `min-h-0` and `overflow-hidden`. Keep the page header outside the table scroll area.
- Let the reusable Table manage available row height and keep pagination visible. Do not add a second competing page scrollbar.
- Use the global scrollbar styling. Do not add browser-default bulky scrollbars or a separate scrollbar design per screen.
- Support small screens with responsive grids and horizontal table scrolling.

## Before finishing

- Confirm existing wrappers were reused and all new custom types/constants are in their folders.
- Check for hardcoded colors, radii, arbitrary spacing and inline styles; replace them with shared tokens/utilities.
- Preserve keyboard focus, accessible labels, validation, empty states and loading states.
- Do not show fake successful backend actions. Clearly handle unavailable functionality.
- Run the appropriate checks for code changes, including TypeScript when types or component props change.
